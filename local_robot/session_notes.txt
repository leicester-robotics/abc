========================================================================
2. Model choice
========================================================================

Two published policy families exist. prepare.py downloads them.

ABC-DiT XL (chosen first, and it is the smallest published model):

- Every published DiT checkpoint is the same architecture.
- Built on CPU with no weights: "DiTPolicy built: 2.016B params"
  (command: CUDA_VISIBLE_DEVICES= uv run python -m abc_minimal.dit)
- Checkpoint used: cache/bottles_75k.pt
  prepare.py key: checkpoints/bottles_release_prep_75k.pt
  Size on disk: about 8.1 GB fp32 (download reported 8063.0 MB)
- Download command that was run: uv run prepare.py --checkpoint
  It also unpacked bottles_in_bin_preview.tar (161.9 MB) and norm_stats.json
  into cache/ (train_real, val_real, train_sim, val_sim previews).
- Download rate was roughly 50-60 MB/s and finished during the chat.
- Vision: DINOv3 ViT-B/16, bundled in the checkpoint (no separate DINO download
  for this eval checkpoint).
- Text: OpenAI CLIP ViT-B/32 text tower, 512-d normalized embedding.
  abc_minimal/dit.py task_name_to_prompt / CLIPTextEmbedder.
  Any free-form English string can be encoded. Quality is only expected near
  the training distribution. bottles_75k was trained for putting plastic
  bottles in a bin (README prompt: "throw plastic bottles in bin").
  A prompt like "pick up the cube" will run, but the policy was not trained
  for that scene.
- Actions: 14-d (6 joints + gripper, both arms), chunks of future joint targets.
  Default diffusion / flow steps in deploy: 10. This session used 5.
- DiT shape from abc_minimal/config.py DiTConfig: hidden 1536, depth 32,
  24 heads. There is a smaller head config (hidden 512, depth 8) used by the
  VLA action head, not as a standalone pretrained DiT.
- DAgger checkpoints (folding_paper_box, insert_earbuds_1eb, insert_earbuds_3eb,
  using_a_key, pack_student_bag) are the same ~8.1 GB DiT. They were finetuned
  on the authors' station, some with 2x arm stiffness and a task-specific
  --init-q. They were not downloaded in this chat. prepare.py --dagger-checkpoint
  NAME prints the deploy command.

ABC-VLA (requested later, not the small model):

- Gemma 3 4B + SigLIP at 224, plus a small AdaLN DiT action head.
- Upstream README: inference wants about 24 GB of GPU. This laptop has 8 GB.
- Checkpoint: cache/vla_abc130k_200000_v2.pt via uv run prepare.py --vla-pretrained
  (a background prepare was observed running during the camera fix).
- V2 checkpoints embed norm_stats.
- Chunk length 30. RTC prefix plus execute-chunk-dim must stay <= 30.
- Prompt is tokenized by the Gemma preprocessor, not CLIP. Live prompt changes
  still work; the 1.3 GB token embedding table stays on CPU and text embeddings
  are cached until the prompt changes (a few milliseconds). Image tokens change
  every observation, so attention KV cannot be cached across frames.
- Gemma weights are under the Google Gemma Terms of Use.

Why DiT first: it is the only smaller published policy. VLA does not fit in
fp32 or even fully in bf16 on 8 GB without offload (bf16 Gemma is on the order
of 8 GB of weights before activations).

========================================================================
3. Why the stock server cannot load DiT on this GPU
========================================================================

Stock entry point: deploy/serve_policy.py
It builds deploy.policy.Policy -> abc_minimal.policy.DiTInferencePolicy.

The constructor does this before any cast:

    self.model = DiTPolicy(self.model_config).to(self.device)
    ckpt = load_pretrained(self.model, checkpoint)

2.016e9 parameters times 4 bytes is about 8.06 GB of fp32 weights, on an
8188 MiB GPU that also runs the display. Activations need more on top.
This was reasoned from the parameter count and the source. The stock server
was NOT launched to confirm an out-of-memory error.

--policy.fast-inference does cast to bf16 and torch.compile sample_actions,
but only AFTER the fp32 model is already on the GPU (see
DiTInferencePolicy._compile_for_fast_inference). It also compiles, which is
slow. It does not solve the load.

Why a separate file: AGENTS.md says preserve forked code and keep local
changes separate. First workaround: local_robot/serve_bf16.py

What serve_bf16.py does (still in the tree, still usable):

- Subclasses DiTInferencePolicy.
- Builds DiTPolicy on CPU (no .to(device) first).
- load_pretrained on CPU.
- model.to(dtype=torch.bfloat16).to(device), then img_backbone.set_bfloat16(True).
- CLIP text embedder on GPU; task vector stored in bf16.
- LivePromptPolicy overrides obs["prompt"] on every infer from a string that
  a daemon thread reads from stdin (type a line, Enter).
- Warmup: 3 dummy zero observations, then prints ms/chunk and peak allocated GPU.
- Serves deploy.websocket_server.WebsocketPolicyServer on 0.0.0.0:8000.
- Refuses nothing about fast_inference anymore (see agent 6). Originally main()
  raised ValueError if --policy.fast-inference was set. That guard was removed
  so DeployPolicy.__init__ can call enable_fast_inference. The extra bf16 cast
  inside enable_fast_inference is a no-op on an already-bf16 model.

Measured warmup of serve_bf16, zero images, 5 diffusion steps, GPU otherwise
quiet enough to load:

    [serve_bf16] warmup: 105 ms/chunk, 4.06 GiB peak GPU

That test server was then killed so port 8000 was free. Later the user started
their own serve_bf16 on port 8000 and agents were told not to kill it.

serve_local.py later became the launcher default for both DiT and VLA.
serve_bf16.py was left working. For DiT, serve_local reuses LivePromptPolicy
from serve_bf16 (same bf16 load path).

Control loop context used throughout:

- Policy dt = 0.03333 s (30 Hz) in deploy/robot/config.py
- RTC: next inference starts rtc_inference_lead_steps before the chunk ends.
- Lead 7 was described in the README as a nominal ~233 ms budget
  (7 * 33.33 ms). Profiling later measured the REAL window at about 211 ms
  (6 sleeps of dt plus 7 short steps). See section 6.

4. Camera crash (SubscribeTimeout on camera:top)
========================================================================

User command (terminal 10), after the server was already up:

    ROBOT_PROFILE=local_yam_config uv run deploy/deploy_policy.py \
      --checkpoint-path=cache/bottles_75k.pt --remote-host=localhost \
      --diffusion-steps=5--rtc --rtc-prefix-length=4 \
      --rtc-inference-lead-steps=7 --execute-chunk-dim=16 \
      --prompt='pick up the cube' --no-record --debug

The pasted line shows --diffusion-steps=5--rtc with no space. The camera
agent later found that tyro rejects that: invalid literal for int() with
base 10: '5--rtc'. So the run that actually crashed must have had a space
(--diffusion-steps=5 --rtc). The log shows "Policy server ready" and then:

    deploy.robot.communication.SubscribeTimeout:
    no message on camera:top within 500ms

Stack: policy_rollout.run -> env.reset -> YAMEnv.get_obs -> _get_camera_obs
-> comms.subscribe, timeout 500 ms. This is NOT a GPU or model failure.
"Policy server ready" means the bf16 server had loaded.

Root cause (agent 1): startup race.

- All three D405s enumerated on USB3 (5 Gbit/s) behind one hub. Serials match
  local_yam_config. Hardware was fine. Camera nodes did not crash.
- Each camera's first frame arrives about 1.3 s after its process starts
  (spawn, pyrealsense2 import, pipeline start).
- deploy_policy starts cameras and the rollout together.
- Because the policy server was already running, the rollout connected
  immediately and called env.reset().
- In --debug, reset skips the follower wait and reads each camera with a
  fixed 500 ms timeout, so it failed on camera:top.
- The agent reproduced the same error with the upstream script.

Fix (upstream files not edited):

- local_robot/policy_rollout.py monkeypatches YAMEnv.reset.
  First reset subscribes to every camera with timeout 30_000 ms
  (CAMERA_BOOTUP_TIMEOUT_MS) before the upstream reset.
  Current code prints "Waiting..." / "All cameras publishing." only when
  DEPLOY_VERBOSE is set. The agent's first verification printed those lines;
  the verbose gate may have been tightened later. The wait itself is unconditional.
- local_robot/deploy_policy.py is the upstream CLI, but it rewrites the
  rollout process target from deploy.robot.gym.policy_rollout to
  local_robot.policy_rollout.

Verification (debug only, no arm motion): upstream script still failed the
same way; the wrapper got through reset (all three cameras) to
"IDLE — press a/b to start inference". Stopped with SIGINT. User's serve_bf16
on port 8000 was left running.

Corrected manual command (space restored, local entry point):

    ROBOT_PROFILE=local_yam_config uv run python -m local_robot.deploy_policy \
      --checkpoint-path=cache/bottles_75k.pt --remote-host=localhost \
      --diffusion-steps=5 --rtc --rtc-prefix-length=4 \
      --rtc-inference-lead-steps=7 --execute-chunk-dim=16 \
      --prompt='pick up the cube' --no-record --debug

--debug starts no follower processes and sets execute_actions=False, so it
does not command the arms. Drop --debug only when you want motion.

5. Enter did nothing at the first-action safety check
========================================================================

After the camera fix, the user ran the local deploy command (with the space)
in --debug, pressed a, got the FIRST RTC ACTION SAFETY CHECK table, and
pressing Enter appeared to do nothing.

The table they pasted (debug, so "Current" is init_q, not a live encoder read):

    Max |delta| from current state: 0.0683 rad (3.9 degrees)
    Action chunk shape: (16, 14)
    Later steps in the chunk: about 0.006 to 0.012 rad (about 0.4 to 0.7 degrees)

    L_J1 +0.5000 -> +0.5450, L_J2 +1.0000 -> +1.0130, L_J3 -1.0000 -> -0.9735
    R_J3 -1.0000 -> -0.9317 was the largest single joint step (+0.0683)

Those deltas are small. The safety check is still required before any
non-debug execution.

Root cause (agent 3), two layered problems:

1. Cosmetic / misleading. With --no-record, both the rollout and
   deploy/robot/key_listeners/key_listener.py read the same terminal.
   The listener calls tty.setcbreak, which turns echo off, so Enter prints
   no newline. After the prompt, the RTC loop prints nothing per chunk while
   inference keeps up, and --debug moves nothing. The session looks frozen
   even when it is running. The user's stuck session had actually passed the
   prompt and executed 285 chunks; output continued on the prompt line.

2. A real race. The listener polls the tty with select + read(1). If it wins
   the Enter, it publishes key "\n", which nothing handles, and input() in
   deploy/robot/gym/policy_safety.py blocks forever. Upstream has no handoff
   that pauses the listener during the safety check.

Fix, only in local_robot/policy_rollout.py, and only when the keyboard episode
controller is active (--no-record / direct episode keys):

- The safety table is still printed by the upstream function, with enter_prompt=None
  so it does not call input().
- Confirmation is read from the key listener's already-published key stream.
- Keys typed before the table is shown are drained and do not count, except
  shutdown keys (c/j) which abort.
- Prompt text: "Press ENTER to execute, c/j to shut down, or Ctrl-C to abort > "
- On Enter: "Confirmed. Executing; press a/b to stop and go home, c/j to shut down."
- --record runs still use upstream input(), because that path does not share
  the cbreak listener the same way (the recorder owns episode control).

Verification via a pseudo-terminal (not by the user typing), --debug only:

- a, then Enter, printed Confirmed. Executing.
- b printed "Episode stopped by operator after 10 chunks", went home, IDLE.
- c exited 0.
- Ctrl-C or c at the prompt aborted before any chunk.
- To free cameras, the agent SIGINT'd the user's stale debug session
  (same as Ctrl-C). It did not kill the policy server on port 8000.
- ruff was not installed, so that agent did not lint.

The user's next real attempt (after this fix) did show:

    Press ENTER to execute, c/j to shut down, or Ctrl-C to abort >
    Confirmed. Executing; press a/b to stop and go home, c/j to shut down.
    WARNING: Chunk 34: inference is still pending; the robot may pause between chunks.

So Enter worked. The warning is section 6.

========================================================================
6. "inference is still pending" and the latency profile
========================================================================

Meaning: RTC starts the next inference near the end of the current chunk.
If that inference is not finished when the chunk runs out, the robot waits.
It is a timing stall, not a crash and not a bad action.

Nominal README budget at lead 7: about 233 ms. Profiling measured the actual
window at about 211 ms (6 sleeps of dt plus the short steps). In the user's
live debug run, 80 percent of chunks landed at exactly 211-213 ms, which means
inference had finished early and the loop was waiting on the control clock.

Steady state, real 480x640 frames from all three D405s, user's live serve_bf16,
5 diffusion steps, n=150 raw frames (agent 4):

    End-to-end median 113.9 ms, p90 121.2 ms, max 258 ms
    With --compress-images, n=100: median 106.8 ms, p90 114.7 ms, max 156 ms

Ranked stages (median / p90 / max, milliseconds):

    1. DiT sampler, 5 steps          95.8 / 97.3 / 104
       19.2 ms per step, 0.59 ms per block
    2. DINOv3 + pooling               6.2 / 6.5 / 11.8
    3. Client msgpack pack            4.5 / 5.4 / 11.6
       (0.36 ms if arrays are contiguous)
    4. Websocket, 2.76 MB payload     2.1 / 2.8 / 3.7
    5. Server CPU preprocess, 3 cams  2.1 / 2.3 / 2.6
       (about 0.5 ms if done on GPU from pinned memory)
    6. Camera read + obs assembly     0.7 / 0.8 / 1.4
    7. Unpack, copy back, unnormalize, response pack  under 0.4
    CLIP text                         0 when the prompt is unchanged (cached)

Stage sum (~106 ms server time) matched measured server time (~108 ms).
A second full copy of the model would not fit in the ~3.5 GB free while the
user's server was loaded, so the GPU rows were measured on a real DiTPolicy
built at depth 2 and depth 6 with random bf16 weights and extrapolated to
depth 32. Treat the per-stage GPU split as an extrapolation; the end-to-end
113.9 ms is a live measurement against the real server.

Why the sampler dominates: each diffusion step reads about 3.8 GB of bf16 DiT
weights at about 200 GB/s, about 78 percent of this GPU's peak bandwidth.
Eager wall time roughly equals GPU time. Python and kernel launch are not
the limit. Laptop was on AC. GPU clocks sagged from 2565 MHz to about 2130 MHz
under a software power cap (~36 W during inference, 55 W cap when a second
process was present). Memory clock stayed at 8001 MHz, so the sag matters
little because the work is bandwidth-bound. CPU governor was powersave with
EPP performance. No GIL issue: inference runs in the server event loop; the
only other thread is the prompt reader. No GC or cuDNN autotune spikes were seen.

Pending warnings were bursts, not a steady shortfall:

- 15 of 74 chunks in one 40 s window, and 14 of 153 in another, all consecutive.
- During a burst, a second CUDA process (/tmp/w8_triton2.py, the VLA agent's
  int8 benchmark) pushed GPU memory from about 4.6 GB to 5.6 GB, utilization
  to 100 percent, and power to the 55 W cap.
- Probe requests jumped from ~108 ms to 222-250 ms at the same moment.
- Outside bursts: zero overruns, max about 123 ms.

So yes: the slowness the user saw (the pending warning at chunk 34, and the
earlier warnings) was other GPU work, not the policy being too slow for the
robot when the GPU is exclusive.

Recommendations, by impact (agent 4). What was later adopted is in section 10.

1. Keep the GPU to the policy server during rollouts. This removed every
   overrun that was measured.
2. If the GPU must be shared, --rtc-inference-lead-steps=10. Window grows to
   about 318 ms (tolerates about 2.8x). Observations are about 100 ms staler.
3. Compiled bf16: about -17 ms (16 percent) per chunk, extra VRAM under 0.1 GB
   in the depth-2/6 measurement (max-autotune). NOT verified at depth 32 in
   that pass, because of VRAM. The suggested code change was to delete the
   ValueError guard in serve_bf16 main and pass --policy.rtc-prefix-length=4
   so the RTC sampler compiles at startup. Compile was about 1 minute at
   depth 6; several minutes were expected at full depth. Agent 6 later
   measured full depth; see that subsection. Compile stayed opt-in.
4. Fewer diffusion steps: about -20 ms per step removed (4 steps ~87 ms,
   3 steps ~67 ms of sampler, from the extrapolation). Quality risk. The step
   count that matters is the SERVER flag --policy.diffusion-steps. The robot
   side --diffusion-steps is recorder metadata only.
5. --compress-images: about -7 ms, payload 2.76 MB to about 19 KB. Caveat:
   OpenCV resize without the server's antialiasing, JPEG quality 75.
6. Not worth it: GPU preprocess / pinned memory (-1.7 ms), making client
   arrays contiguous (-5 ms, and it would need an upstream edit), cudnn.benchmark
   and TF32 (not measured; model is bf16 and the only conv is DINO patch embed).

Profiling method: passive ZMQ listening plus scripts under /tmp/abc_prof/.
No actions were sent. Probe requests to port 8000 were timed into the gap
after the user's chunks. The user's server and debug rollout were left running.

7. Start pose
========================================================================

Yes. A policy should start from the pose it was trained from, and the deploy
stack already does this for non-debug runs.

YAMEnv.reset() (deploy/robot/gym/yam_env.py) commands each arm to
config.robots[name].init_q before the episode.

local_yam_config uses upstream _DEFAULT_INIT_Q, the same pose as the gtwy_config
profile the upstream README uses for bottles_75k. Per arm, J0 through gripper:

    [0.0, 0.5, 1.0, -1.0, 0.0, 0.0, 1.0]

That is the "Current" column in the debug safety table. In --debug the arms
are not moved, and _get_state_obs returns get_init_q(), so that column is the
assumed pose, not a measurement.

The physical arms rest near the base pose (joints near zero, per AGENTS.md).
The first real episode therefore moves them from near zero to init_q:
0.5 rad on J1 and 1.0 rad on J2 and J3. That first move is large even though
the policy's first action relative to init_q was only 3.9 degrees.

What upstream reset actually does (read by the launcher agent):

- One follower interp command: a straight-line ramp of FOLLOWER_INTERP_S = 2.0 s
  from wherever the arm is to init_q, no easing, whatever the distance.
- From the base pose that is about 1 rad on J2/J3 at 0.5 rad/s, with an abrupt
  start and stop.
- After b (go home) from a far pose, the same 2 s interp can exceed 1 rad/s.
- c/j shutdown moves the arms toward zero in 2 s from wherever they are.
  Press b (home) before c, so that shutdown move is short.

Gentle reset added later (local_robot/policy_rollout.py, env LOCAL_RESET_SPEED,
set by run_policy --reset-speed, default 0.25):

- Only when execute_actions is true (so --debug does not move arms).
- Splits the move into several of the same 2 s ramps through waypoints.
  segments = ceil(max |target-start| / (speed * 2.0)).
- Default 0.25 rad/s: base pose to init_q is 2 ramps of 0.5 rad, about 4 s.
- --reset-speed=0 or unsetting the env var keeps upstream behavior.
- Running deploy_policy directly does not set the env var, so it stays upstream
  unless you export LOCAL_RESET_SPEED.
- The first-action safety check is unchanged and still happens after the move
  to init_q, on the first policy chunk.
- This gentle move has NEVER been executed on the real arms. All verification
  was --debug or offline. Watch the first live reset. Keep a hand at the e-stop.

Camera placement, table height, and objects matter more than the exact start
pose for bottles_75k, because the checkpoint was trained on the authors'
station. DAgger checkpoints need their own --init-q printed by prepare.py.
Joint angles matching init_q does not fix a different camera rig.

The preview episodes in cache/ could be checked for the recorded start pose.
That comparison was offered in chat and was not done.

8. One-command launcher
========================================================================

User asked for one smooth way to run all of the above. Agent 5 built it.
Agent 6 then pointed it at the VLA-capable server and added policy-aware defaults.
Current behavior is what is in the files now (section 10 and agent 6).

local_robot/run_policy.py:

- Sets ROBOT_PROFILE itself (default local_yam_config; --profile overrides).
- Preflight, read-only:
    no other deploy/run_policy/dagger session
    CAN links up (warning under --debug if not)
    RealSense devices not held by another process (yam-harness serve is the
    example called out) and on USB3
    checkpoint exists and its sniffed kind matches --policy if given
    port free, or an existing policy server on that port (websocket probe);
    reuse does not stop that server; --no-reuse refuses instead
    a non-policy process on the port is an error
    free VRAM: default minimum 4.5 GiB for DiT, 2.9 GiB for VLA
    other GPU processes above 256 MiB are warned
- Starts local_robot.serve_local by default (--server-module can still be
  local_robot.serve_bf16, which is refused for a VLA checkpoint).
- Passes one set of flags to the server: checkpoint, policy type, diffusion
  steps, prompt, port, rtc prefix, optional fast-inference, optional
  --offload.quantize. --server-args may not repeat those managed flags.
- Server stdout/stderr go to data/logs/server-*.log.
- Prompt channel: the launcher owns the server's stdin pipe and listens on
  the unix socket /tmp/abc-$USER/prompt-<port>.sock.
  local_robot/set_prompt.py connects, sends one line, and the launcher writes
  it to the server stdin, then waits until the log shows "[prompt] now:".
  This works ONLY for a server the launcher started. A reused server: type
  the prompt in that server's own terminal. set_prompt says so if the socket
  is missing.
  Recordings (if you drop --no-record) keep the launch --prompt, not later
  live prompts.
- Foreground: local_robot.deploy_policy with the same checkpoint and RTC flags.
- On c/j, Ctrl-C, hangup, or a robot-side crash: stop the server child if
  this launcher started it; do not stop a reused server; reap orphaned camera
  and key-listener processes; restore the terminal.
- Prints a banner: profile, checkpoint, prompt, log path, keys.

Defaults now:

    diffusion steps 5 (server)
    RTC on, prefix 4
    lead 7 and execute-chunk-dim 16 for DiT, and for VLA when the GPU is free
    lead 10 and chunk 20 if VLA is auto-switched to int8 or the GPU is shared
    --no-record
    --reset-speed 0.25
    prompt default if you omit --prompt: "throw plastic bottles in bin"
    (the README examples pass "pick up the cube")

Policy-aware VLA switch (run_policy._choose_rollout):

- If other GPU compute apps exist, OR free VRAM is under 7.2 GiB, AND the
  launcher is starting the server itself (not reusing one), AND the user did
  not already pass --offload.quantize in --server-args:
  it appends --offload.quantize=all and prints that it switched.
- VLA bf16 on a shared GPU without that switch is warned: most Gemma layers
  stream, about 450 ms/chunk, expect pending pauses.
- --fast-inference is refused for VLA.
- RTC check: 1 <= prefix <= lead < execute-chunk-dim, and prefix + chunk <= 30
  (both DiT and VLA chunk_length used here is 30; DiTConfig and VLAModelConfig).

Verification of the launcher (agent 5), --debug, pty, before VLA integration:

- a, safety table, ENTER, 18 chunks, set_prompt changed the prompt (server log),
  b, c, exit 0, terminal restored, nothing left running.
- Ctrl-C mid-episode cleaned up.
- Closing the terminal (hangup) still cleaned up orphaned camera nodes,
  key listener, and the server.
- A camera-busy failure (another harness grabbed a camera after preflight)
  still stopped the server.
- Not run: kill -9, and an end-to-end reuse of a real policy server (reuse
  was tested with a stand-in).
- An early port probe left one harmless traceback in the user's serve_bf16
  terminal. The server kept running. The probe was fixed.
- The gentle reset was not run on the arms.

Agent 6's later debug end-to-end used synthetic camera frames because a real
preflight refused (yam-harness held the cameras). See agent 6. Those runs
also saw zero "pending" warnings.

9. VLA GPU/CPU offload
========================================================================

User asked for the serve script to also run ABC-VLA, with GPU/CPU offload,
as efficient as this machine allows. Agent 2 built it without editing
serve_bf16.py or any upstream file.

Files:

- local_robot/serve_local.py
  Auto-detects dit vs vla via deploy.policy.selector.sniff_policy_kind
  (--policy-type overrides). DiT uses LivePromptPolicy from serve_bf16.
  VLA uses OffloadVLAInferencePolicy. Same stdin live prompt. Warmup prints
  ms/chunk, peak allocated GPU, reserved GPU, pinned host bytes, and (after
  agent 6) startup seconds and fast_inference flag.
- local_robot/vla_offload.py
- local_robot/bench_serve_local.py
  Replays real frames from cache/val_real through the same policy object.
  --save / --compare for action diffs. No robot.

Design (why these choices):

- Checkpoint is read on CPU with mmap. The model is built without allocating
  full weights, then checkpoint tensors are dropped in. Gemma in the file is
  already bf16. No full fp32 copy on CPU or GPU. Load about 2 s.
- Per observation, Gemma + SigLIP run once. The small action head runs once
  per diffusion step. So SigLIP, projections, state MLP, pooling, and the head
  (fp32, matching upstream) always stay on the GPU.
- Of 34 Gemma decoder layers, as many as fit stay resident. Budget is free
  VRAM at startup minus --offload.reserve-gb (default 0.5), or an explicit
  --offload.gpu-budget-gb.
- The rest live in one exactly sized pinned CPU block and rotate through
  2 preallocated GPU slots, copied on a side CUDA stream with events, spread
  through the stack so the copy of the next layer overlaps compute. The
  rotation carries across requests, so the first streamed layers of the next
  request can load while the robot executes. Nothing is allocated or pinned
  per request.
- Prompt: 1.3 GB token table stays on CPU. Token ids, text embeddings, padded
  ids, and masks are cached until the prompt changes.
- int8 is weight-only, one scale per output row, plain PyTorch (Int8Linear).
  torch._weight_int8pack_mm was about 55 ms per matmul on this GPU, so it was
  not used. torch.compile of the int8 matmul was slower. Quantizing dequantizes
  back to bf16 on the fly, which is why int8 can be SLOWER than resident bf16
  when the GPU is free, and FASTER when the alternative is streaming many
  bf16 layers over PCIe.
- PCIe link measured Gen4 x8 at 12.6 GB/s. About 15 ms per bf16 layer and
  7.5 ms per int8 layer of copy.
- Outputs were checked identical across resident/streamed splits (bf16).
  Cached prompt prep matched upstream exactly.
- --offload.trim-padding (Gemma on 213 real tokens instead of 256) was tested,
  outputs identical, only about 4 ms saved, left off by default.
- int8 is off by default because it changes actions and is slower on a free GPU.
